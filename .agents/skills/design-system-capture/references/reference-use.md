# Using external DESIGN.md references

Reference libraries such as VoltAgent's Awesome DESIGN.md are useful for
learning how mature systems express roles, hierarchy, responsive behavior, and
component character. They are not drop-in themes for an existing brand.

## Select by problem, not prestige

Choose two or three references that answer a concrete question:

- dense product UI and keyboard-first operation;
- financial trust and numeric precision;
- editorial hierarchy and restrained surfaces;
- mobile transaction flows;
- dual-theme data visualization;
- high-touch or luxury service without ornamental excess.

For each reference, record the narrow pattern, why it works, and what conflicts
with the current product. Extract roles and decision rules, not trademarked
motifs, proprietary assets, or an entire palette.

## Reconcile with incumbent truth

Map compatible ideas into the project's existing semantic tokens and
components. When a reference suggests a new role or state, label it proposed
until the user approves it and implementation exists. Never overwrite an
existing `DESIGN.md` merely because a public example is more polished.

## Attribution and safety

Keep source links in working notes when they informed a consequential decision.
Review the source license before copying substantial text or assets. Publicly
visible CSS values can inform analysis, but the resulting system must remain a
description of the user's product, not a claim of affiliation with the source
brand.

Google's DESIGN.md work and the Awesome DESIGN.md collection informed the
schema and reference workflow in this skill.
